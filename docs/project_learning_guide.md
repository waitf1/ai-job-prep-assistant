## 1. 先理解这个软件在做什么

一句话：把简历和项目资料交给系统，再告诉它目标岗位，系统给出分析与建议，并陪你练习面试。

你看到四个页面：岗位分析、模拟面试、资料库、历史记录。它们不是四个模型，而是四种业务入口。

可以把大模型想成一位通过电话联系的顾问。你的程序负责整理材料、安排提问顺序、检查回答格式、记录过程和保存结果。顾问擅长理解语言，但可能说错话；程序不能因为回答流畅就全部相信。

**整个项目是服务流程，大模型只是其中一个参与者。** 你没有训练自己的大模型，而是在开发一个使用现有模型能力的软件。

先分清四类东西：

- 代码：规定步骤，比如检查输入、查询资料、保存记录。
- 数据：简历、JD、项目片段、面试回答。
- 模型：理解材料并生成语言内容的能力。
- 界面：按钮、输入框、标签页，让人操作程序。

界面好看不等于模型回答更准确；分析逻辑改变也不一定需要改界面。

## 2. 读项目必需的 Python 基础

### 2.1 变量、字符串、列表和字典

    resume_text = '我用 Python 做过一个网站。'
    skills = ['Python', 'SQL']
    result = {'skills': skills, 'score': 80}

字符串是一段文字；列表按顺序放多个值；字典通过名称取值。result['score'] 取出 80。

result.get('score', 0) 在没有 score 时返回默认值 0。但模型没提供分数，不一定意味着用户应该得零分。默认值方便使用，也可能掩盖错误。

### 2.2 函数：把一段步骤起个名字

    def has_text(text):
        return bool(text.strip())

def 定义函数，括号中是输入，return 返回结果。strip() 去掉两端空白，避免把空格当成有效内容。

读项目函数时，先看输入和返回值，再看处理步骤。不要第一遍就纠结每一个语法。

### 2.3 类、对象和 self

InterviewSession 是一场面试的数据格式；某个 session 对象是你正在进行的具体面试，里面有问题、轮次和状态。

InterviewSessionService 负责开始、提交回答和结束面试。数据和操作分开，更容易保存与测试。

self 表示当前对象。self.model 是这个客户端使用的模型对象，不是全局魔法变量。

### 2.4 dataclass 与类型标注

    from dataclasses import dataclass

    @dataclass
    class Feedback:
        score: int
        comment: str

    feedback = Feedback(80, '可以补充具体例子')

dataclass 帮助生成初始化等重复代码。类型标注 score: int 表示期望整数，但一般不会自动阻止传入字符串，运行时仍需检查。

frozen=True 阻止常规方式重新赋值字段，但不是深度冻结：字段里的列表也不会自动变成不可修改。

### 2.5 异常与错误处理

    if not resume_text.strip():
        raise ValueError('请提供完整简历')

raise 表示当前路径不能继续。上层用 try/except 接住错误，再显示提示。

不要用一个大 except 把所有错误吞掉。明确告诉用户失败，通常比假装成功更可靠。

### 2.6 import、Path、装饰器

import 引用其他模块；Path 帮你组合文件路径；装饰器写在函数前，比如 @st.cache_resource，用于改变函数的使用方式。

项目通过 Path(__file__) 定位源码位置，再找到 prompts 目录，减少对终端当前目录的依赖。

### 2.7 None 与布尔值

int | None 表示整数或没有该值。面试 max_rounds 为 None 代表循环模式，不是零轮。

    bool(False)    # False
    bool('false')  # True，非空字符串会被当成真

因此不能随便用 bool() 处理模型返回的 use_search。字符串 false 和真正的布尔值是两回事，这也是本项目修复过的边界问题。

## 3. 点击开始分析以后，究竟发生了什么

假设虚构用户小林的简历写着：使用 Flask 和 SQLite 完成课程网站。JD 要求：Python、接口开发、数据库基础。

### 第一步：读取并检查输入

app/main.py 生成页面。输入由组件和 st.session_state 保存。run_analysis() 检查 JD、简历和上传解析状态；材料不足直接提示，不请求模型。

### 第二步：组织工作流

JobPrepWorkflow 是流程组织者，连接 JD 分析、匹配、建议、面试准备等服务。

### 第三步：先分析岗位

JDAnalyzer 读取 Prompt 模板，填入 JD，调用 LLMClient。模型返回 JSON 文本，程序解析成 JDAnalysisResult。

这时拿到职责、技能、加分项等字段，不只是一大段自由回答。

### 第四步：准备候选人的材料

普通模式使用当前简历；RAG 模式从简历库选全文，并在受限流程中决定是否检索项目证据。

模型不能任意搜索你的电脑。它只能申请使用程序提供的检索工具。

### 第五步：分析匹配关系

JobMatchAnalyzer 收到简历、JD、结构化岗位要求及可选证据。例如模型可能判断 Flask 经历支持接口开发，但简历没有体现部署经验。

代码检查格式并核对引用，业务判断本身仍来自模型。

### 第六步：生成建议与面试准备

ResumeAdvisor 区分已有经历可以直接改写的表达和完成新工作后才能写入的表达。InterviewPreparer 生成问题与短期准备方向。

正常普通分析有 JD、匹配、建议、准备四个主要语言模型调用。RAG 可能增加规划和重排序调用，实际请求次数还受路径与 SDK 重试影响。

### 第七步：展示和保存

结果先放进当前会话，界面用标签页展示。用户点击保存才写入历史库。生成建议不会自动覆盖你的简历原文件。

记忆路线：

    用户输入
      → main.py 校验
      → JobPrepWorkflow 编排
      → 各业务服务组织 Prompt
      → LLMClient 调用模型
      → 解析与校验响应
      → 页面展示
      → 用户主动保存历史

自查：模型断网是否所有功能都失效？不是。历史查看、部分本地资料操作仍可以工作。

## 4. LLM、API、OneAPI、LangChain 分别是什么

### 4.1 LLM：处理语言的大模型

模型根据本次提供的上下文生成内容。它可能给出合理建议，也可能虚构细节。把文件上传进资料库，不等于模型永久学会了文件；程序要把相关文字放入请求。

模型输出也不是普通计算函数那样完全确定。相同输入可能得到不同措辞或判断。所以需要区分程序行为测试和真实模型效果评测。

### 4.2 API：供程序使用的服务入口

网页供人点击，API 供程序发送规定格式的请求。模型调用主要需要：

- Base URL：发往哪里。
- API Key：调用凭证。
- Model：选择哪个模型。
- Messages：这次的指令与材料。

localhost:8501 通常是 Streamlit 页面，不是模型 API。把两个地址混淆，就像把业务信件寄到了展示窗口。

### 4.3 HTTP 与 JSON

HTTP 是常见网络通信规则；JSON 是数据交换格式。JSON 是文本，解析后可成为 Python 字典。

JSON 的对象字段名使用双引号，布尔值是 true/false；Python 是 True/False。json.loads() 负责解析。

语法合法不等于业务合法：score 的值即使是合法字符串，也不符合要求整数分数的规则。

### 4.4 OneAI／OneAPI

项目使用配置的 OpenAI 兼容入口请求模型。OneAPI 可以充当中转，把请求转交上游；实际转发情况取决于你的配置。

因此错误可能出在应用、中转或上游。502 常表示网关未取得有效上游响应，但仅凭状态码不能确定是哪一个具体服务故障。

### 4.5 LangChain 与 ChatOpenAI

本项目主要通过 langchain_openai.ChatOpenAI 包装聊天请求与工具绑定。invoke() 执行调用，bind_tools() 告诉模型可申请哪些工具。

LangChain 不是模型，也不是只要安装就自动拥有 Agent。即使用直接 HTTP 或其他兼容 SDK，也可以实现相似流程。

### 4.6 httpx 与代理

httpx 是网络请求库。终端继承代理变量时，发给本机 OneAPI 的请求可能错误绕到代理上。项目对回环地址使用直接连接。

这不等于关闭 HTTPS 校验，也不是所有 502 的解决办法。

### 4.7 token、temperature、上下文

token 是模型处理文字的单位，不固定等于一个汉字或单词。更长的输入通常消耗更多 token，具体计数由模型分词规则决定。

temperature 调整随机性倾向，较低通常更稳定，但不是准确性开关。

上下文是本次交给模型的内容。你的 Python session 里有历史，不代表模型自动知道历史；程序必须再次提供所需信息。

## 5. Prompt：给模型的任务说明

模板在 prompts 目录，按任务分开。system 模板说明角色和限制；user 模板放本次材料和输出格式。

    template = '请从以下 JD 提取技能：{job_description}'
    prompt = template.format(job_description='要求 Python 和数据库经验')

模板中的双花括号用于保留字面 JSON 括号，因为 Python format 会把单花括号视为替换位置。

好的 Prompt 要说明：依据什么材料、返回什么字段、什么不能编造、资料不足怎么办。用户上传的内容属于数据，不能因此获得修改系统规则的权限；这涉及 Prompt 注入风险，当前项目未声称全面防护。

模型收到“必须返回整数”仍可能返回字符串。所以 Prompt 负责引导，代码负责验证。

推荐打开 jd_analysis_system.txt、jd_analysis_user.txt、JDAnalyzer.analyze()、parse_json_response()，连起来读。学会这条短链，就容易理解其他服务。

## 6. 文件解析与两种模型

### 6.1 文件解析：先拿到文字

PDF、Word 是文件格式，需要提取文字。PyMuPDF 处理 PDF；python-docx 处理 Word 段落和表格；TXT、Markdown 做编码解码。

解析只是拿到文字，不是理解含义。当前没有 OCR，扫描图片型 PDF 可能读不到内容；复杂多栏排版也不保证阅读顺序完全正确。

### 6.2 embedding 模型：把文字编码成数字

为了比较语义相似性，embedding 模型把文本转成向量。向量是一串数字，可以粗略理解为多维空间中的位置。

    开发网站接口 → 一串数字 A
    实现后端 API → 一串数字 B
    制作财务报表 → 一串数字 C

前两句字面不同，却可能在向量上较接近。上面不是实际模型输出，只是说明思路。

当前默认 embedding 模型为 BAAI/bge-small-zh-v1.5，通过 Sentence Transformers 相关封装使用。它负责文本编码，不负责生成整篇简历建议。

聊天模型和 embedding 模型承担不同任务，不能混为一谈。

### 6.3 Chroma：保存向量、正文与来源

查询时把 query 转成向量，再查找较近记录。collection 是库里的一个集合，项目证据与简历选择索引分开管理。

元数据是关于正文的信息，例如文件名、章节、片段编号和清洗状态。没有它，找到内容也难以说明来源。

换 embedding 模型后，旧向量和新向量未必能比较。不能只改模型名就默认旧索引仍正确。

向量距离不是能力分数或匹配概率。阈值依赖模型、距离方式和数据，不是通用常数。

## 7. RAG：先找材料，再辅助生成

RAG 是 Retrieval-Augmented Generation，意思是检索增强生成。先从资料里找相关内容，再把内容交给模型回答。

问小林项目怎么测试接口，系统先找测试材料，再分析。它不是训练，也不是让模型永久记住资料库。

### 7.1 入库和查询是两条链

入库：解析 → 去重 → 清洗 → 切片 → 可选 AI 复核 → 向量化 → 保存。

查询：组织 query → 召回候选 → 过滤 → 重排序 → 加入 Prompt → 生成分析。

入库复核问“是否值得保留”，查询重排序问“是否适合本次岗位”。两者目的不同。

### 7.2 为什么切片

项目报告可能很长，包含设计、测试、致谢和参考文献。查询只需相关部分。

太大的片段带入噪音，太小的片段丢上下文。本项目优先参考标题、段落和项目单元，默认目标长度 700 字符。

源码保留 overlap 参数用于旧调用兼容，当前结构切片没有使用固定滑窗重叠。读代码不能只看参数名。

### 7.3 清洗与审核

规则适合清楚的噪音，例如页眉页脚；AI 可以辅助判断内容价值，但增加成本且可能误判。AI 审核失败时保守保留，避免因网络问题丢资料。

更多删除不等于更高质量。没有标注样本时，不应宣称清洗策略一定提升准确率。

### 7.4 召回、过滤、重排序

召回先找一批可能相关内容；过滤去掉明显不适合的；重排序选择真正值得送进最终分析的片段。

默认候选上限 10、最终上限 5。AI 重排序失败回退规则选片；没有有效结果时说明未采用项目证据。正常无结果与服务直接报错不同，后者有时仍会中止分析。

### 7.5 为什么简历全文和项目 RAG 分开

只检索简历的一小段，可能漏掉教育背景、其他经历与限制条件。因此索引帮助选择一份简历，最终核心分析使用这份简历全文。

简历选择索引使用从全文不同位置抽样的短文本。可以理解为通过目录找到原件，而不是把目录当原件。全文仍受输入长度预算限制。

### 7.6 检索不好怎么排查

按顺序问：原文有没有 → 入库了吗 → 召回了吗 → 被哪一步过滤 → 最后是否加入 Prompt。

不要一看到结果不好就只改最后的 Prompt。资料缺失、切片、query、阈值、重排序和最终理解，都可能是原因。

## 8. 工作流、Agent 与 Tool Calling

工作流像菜谱：步骤由代码安排。本项目的 JD、匹配、建议和准备顺序明确，因此固定编排是合理选择。

Agent 的定义在不同工具中不完全一致。判断时看控制权：下一步由代码指定，还是模型根据结果选择？本项目属于固定工作流加受控模型决策，不是无限自主循环或多个智能体讨论。

### 8.1 工具调用的真实过程

    程序：你可以申请使用项目检索工具。
    模型：我希望调用它，query 是这句话。
    程序：检查名称、次数与参数。
    程序：执行检索，交给后续分析。

模型是提出申请，Python 才负责执行。绑定工具不等于工具已经运行，也不意味着模型得到任意执行代码的权限。

Schema 是填写规则：工具叫什么、有哪些参数、类型是什么。发给模型后，程序仍要校验。

目前只接受一次指定检索调用。JSON 规划中的 use_search 必须是真布尔值，不能把字符串 false 当真。

### 8.2 为什么有工具类

ToolResult 统一成功状态、数据和摘要；ToolCallRecord 记录执行情况。统一格式使流程更容易处理错误。

封装成工具不代表都由模型动态选择。JD 工具等仍由固定工作流调用。面试时应该讲实际控制流程，而不是根据类名夸大自主能力。

## 9. 原文引用到底验证什么

引用包括匹配点下标 point_index、来源 source 和原文 quote。程序检查下标与来源，再用字符串查找核对引用是否存在，至少要求 8 个字符。

find() 找到返回起始位置，找不到返回 -1。界面据此提示已核对或未通过。

但如果原文只是“看过教程”，模型推断成“独立完成系统设计”，即使引用存在，推断仍可能错。

因此原文存在不等于经历真实、能力充分、判断正确。当前不强制每条结论有引用，也没有页码跳转；项目引用核对的是本次检索上下文。

新增简历原文引用只在当前分析展示，历史不复制它；项目引用可保留并在恢复时重新核对。

## 10. 内存、文件、SQLite 与哈希

### 10.1 工作台和档案柜

内存像临时工作台，进程结束后不能指望还在；磁盘像档案柜，重启后仍可读取。

session_state 是会话状态，不是永久数据库。用户点击保存后写入 SQLite，才有独立于本次会话的持久化。

### 10.2 为什么用不同存储

简历文件负责全文；Chroma 负责相似性查询；SQLite 负责按 ID、类型和时间管理历史。

Chroma 也可能使用本地数据库文件，但不要直接修改它的内部存储。项目历史库是单独的数据层。

### 10.3 SQLite 的基本概念

SQLite 将数据库保存在本地文件，不需要另外启动数据库服务器。表有固定列，每条记录有自己的值。

SELECT 查询，INSERT 新增，DELETE 删除。项目通过 HistoryStore 统一操作。练习 SQL 不要对真实数据执行删除。

索引像目录，帮助查找；事务将一组数据库操作作为整体，避免只完成一半；外键描述记录之间的关联。

删除关联分析后，面试历史可以解除关联继续保留，而不是必须一起消失。

版本号说明记录使用哪版结构。新增字段时，还要考虑旧记录如何恢复。

### 10.4 哈希不是加密

SHA-256 根据内容生成指纹，用来识别重复或比较版本。原文仍在 JSON 或数据库里时，有读取权限的人仍可能看到。

所以用了哈希，不等于资料已经加密。

## 11. Streamlit 为什么刷新、丢状态或卡顿

### 11.1 操作组件通常会重跑脚本

点击按钮后，不是只运行按钮下面几行，而是重新执行页面脚本。按钮在该次运行中为真，下次重跑可能为假。

如果结果只在按钮分支里临时显示，下一次操作就可能消失。因此分析结果要保存到状态中，再独立渲染。

### 11.2 session_state 和 key

session_state 在重运行之间保存数据；key 是组件身份。key 重复会冲突，组件不显示时绑定值也可能被清理。

preserve_page_inputs() 保留跨页输入。上传文件保存解析后的材料，而不是任意给上传控件状态赋值。

刷新浏览器、切换页面和重启进程不是同一件事。对长期保留数据，只依赖明确的保存操作。

### 11.3 cache_resource

模型或数据库对象初始化昂贵，缓存减少反复创建。但缓存可能被会话共享，不代表自动实现用户隔离，也不代表内容永远有效。

### 11.4 折叠不代表不执行

expander 通常只是初始不展示内容，里面的代码仍可能运行。此前资料库切换慢，与统计触发模型初始化、折叠区提前读取有关。

后来分开不需要 embedding 的读取路径，并用真正条件分支决定是否读取片段。

### 11.5 CSS 只控制外观

CSS 控制字号、颜色、边距和边框。隐藏 Deploy 不是访问控制；权限要由业务层检查。

项目样式依赖部分 Streamlit 页面结构，升级组件后需要视觉检查，Python 测试不能证明排版正确。

## 12. 用状态机理解面试

状态机的意思是当前在哪一步、允许哪些动作。项目主要状态：active 可回答；summary_pending 等待复盘；completed 已完成。

复盘失败后不应重新追加上轮回答，而是只重试总结。否则重复操作会产生重复记录。

理论题需要 JD；项目题需要真实完整简历；题库题需要有效上传题目。题库仅在当前会话保留。

原始回答与模型反馈分开保存，因为用户需要回看当时到底说了什么。“没有相关经历”允许提交，不能要求用户编造。

### 12.1 历史为什么要限长

每轮都重复发送全部历史，单次输入越来越大。若每轮长度相近，整场累计重复发送量可能接近随轮数平方增长。

出题使用最近 8 轮限长内容，完整记录仍保留。复盘采用全程摘录，超过 50 轮抽样。减少输入的代价是模型看不到全部细节，页面必须说明。

评分 100 不是通过面试概率。代码检查数值格式，不能自动证明评分稳定或公平。

## 13. 超时、重试、日志与排错

超时防止无限等待；重试应有限。默认单次超时 60 秒，SDK 最大重试 2 次，不代表整条工作流最多 60 秒。

权限错误不靠连续重试解决；格式错误也不一定适合原样重试。重试可能增加成本。

页面提示面向用户，日志面向开发排查。当前 llm_call 记录调用 ID、模型、Prompt 指纹、字符数、耗时、token 和状态，不记录正文与密钥。

token 为 null 表示不知道，不是没有消耗。耗时包含调用等待，不是纯模型计算耗时。当前没有完整任务追踪或费用看板。

排错顺序：

1. 确定发生在哪个动作：解析、检索、分析、出题或保存。
2. 看最早的相关异常，不只看最后一行。
3. 检查输入、配置名称和服务地址，不公开密钥。
4. 网络问题查服务；JSON 问题查结构；证据问题从入库到召回逐步查。
5. 修复后运行相关测试，再验证业务路径。

不要为模型 JSON 错误去改 CSS，也不要默认页面慢就一定是导航按钮的问题。

## 14. 测试与 Mock

单元测试给固定输入，检查行为。例如字符串 false 不触发检索，不存在的引用核对失败。

Mock 是可控替身。真实模型请求慢、花钱且不稳定，测试可以让假模型固定返回某种结果，专门检查失败路径。

patch 在测试期间替换对象；依赖注入则创建服务时传入客户端替身。这解释了很多服务为什么接受 llm_client 参数。

替身能证明程序如何处理错误，不能证明真实模型通常不会错误。

Streamlit AppTest 模拟组件操作，检查导航、状态和提示；浏览器检查负责真实视觉。两者不能互相完全替代。

当前最近一次 149 项测试通过，不等于覆盖率 100%、没有缺陷或 RAG 准确率 100%。真实效果需要更多标注案例和人工判断。

在项目根目录 PowerShell 运行：

    .\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py" -v

只运行工程边界测试：

    .\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_engineering_quality.py" -v

看到 FAILED，先找测试名和 traceback；看到某些测试环境提示，不要只凭一条警告认定崩溃，应结合最终结果。

## 15. 环境、依赖与隐私

.venv 是项目独立的工具箱，避免不同项目的 Python 库混在一起。明确运行 .venv 中的 python，比依赖终端默认 python 更可靠。

requirements.txt 描述安装哪些库；没有完全锁定版本时，今天和以后安装的版本可能不同。锁定之后仍需新机器验证，模型下载和系统环境也会影响运行。

.env 保存配置，python-dotenv 读取它。API Key 是凭证，不是展示文字。

.gitignore 告诉 Git 忽略什么，但不是加密，也不会撤回已经公开的数据。目前目录尚未建立 Git 与 CI，不能宣称已经有完整版本管理。

本地存储不等于全程离线。执行模型分析时相关材料会发送给配置的服务。当前没有生产级用户隔离或加密存储。

学习优先使用虚构材料，不要把真实简历、终端密钥和历史回答放进公开演示。

## 18. 自测问答与掌握标准

**RAG 会把资料写入模型参数吗？** 不会，主要是检索后放进请求。

**模型自动读取 Chroma 吗？** 不会，程序查询后把内容交给模型。

**用了 LangChain 就是 Agent 吗？** 不是，看谁决定下一步。

**有向量库为什么还用 SQLite？** 语义查询与历史记录管理需求不同。

**合法 JSON 就能直接信吗？** 不够，要检查字段、类型、范围和业务含义。

**project 标签一定代表真实项目题吗？** 不一定，标签合法与语义真实不同。

**改变 UI 能改善模型评分吗？** 不能，它们是不同层面。

**一份真实简历够不够学习？** 足够练流程与边界，但不足以证明跨场景效果。

**为什么不做多 Agent？** 当前任务依赖明确，额外调用与状态复杂度未必值得。

**AI 写了很多代码怎么面对面试？** 如实说明辅助开发，展示自己能解释、核查和修改的内容。

判断是否学会，用四个层次：

- 能解释：不用文档说出一条链路，分清模型、向量库与历史库。
- 能定位：给出一个故障，知道先查哪层。
- 能修改：独立完成一个小改动并验证。
- 能取舍：说清为什么保留全文、为什么限制调用、预算会损失什么。

不要以看完文档为终点。更有说服力的是讲清楚：遇到什么问题，为什么这样设计，怎么验证，还有什么未解决。

## 补充一：带你逐行读懂一个真实服务

打开 app/services/jd_analyzer.py，找到 analyze()。下面按实际执行顺序解释，不要求先掌握全部类语法。

**第一步：读取模板。** load_prompt 从 prompts 文件夹读取 system 与 user 模板。此时只是本地读文件，没有请求模型。如果模板文件名错误，这里就可能失败，与网络无关。

**第二步：填入本次岗位。** user_template.format(job_description=job_description.strip()) 将用户岗位替换进模板。变量名左边对应模板占位符，右边是实际输入。strip 只处理首尾空白，不会自动提炼岗位内容。

**第三步：调用客户端。** self.llm_client.chat(system_prompt, user_prompt) 将两份文字交给统一客户端。客户端检查输入预算，发送请求，记录元数据，然后返回文本。具体调用地址和模型来自配置。

**第四步：解析 JSON。** parse_json_response(response_text) 将返回文本变成 Python 字典。如果模型只输出一段普通说明，解析会失败；如果输出列表，顶层对象检查也会失败。

**第五步：逐字段检查。** ensure_string_list 检查职责、技能等字段是否为字符串列表。当前部分服务对缺失字段仍使用空列表，因此不是所有业务字段都已做严格必填检查。

**第六步：返回数据对象。** JDAnalysisResult 把字段组合成一个对象交给工作流。这个对象不是模型本身，也不是已经保存的数据库记录。

现在反过来问：如果页面的“必备技能”为空，可能是什么原因？可能 JD 本来没有、模型遗漏、默认空列表掩盖了遗漏，或者展示路径有问题。沿上面六步观察，比马上要求模型“再认真一点”更有效。

同样方法可以用来阅读 MatchAnalyzer、ResumeAdvisor 和 InterviewPreparer：找输入、模板、调用、解析、校验、返回。

## 补充二：一场面试的对象是怎么变化的

设想最初 current_question 是“请介绍项目”，rounds 为空，status 为 active。

用户回答后，submit_answer 先确认状态允许回答，再调用模型取得反馈。如果还要继续，必须先得到合法下一题与来源，才追加本轮记录。

成功追加后，rounds 多一条，current_question 改为下一题。current_round_number 根据历史数量计算，不是数据库里一个自动增长字段。

达到设定轮数时，finish 把状态设为 summary_pending，再请求总结。总结成功设置 summary，并将状态改为 completed。

如果总结请求失败，已追加的回答仍在，状态保持 summary_pending。因此页面可以只重试总结。若未取得合法下一题，本次提交可能尚未追加轮次，需要用户重试；不能把不同失败位置都解释为“已经保存了回答”。

理解这个对象的变化，就能知道为什么直接在页面上堆很多 if 判断容易混乱，以及为什么测试要检查状态与记录数量。

## 补充四：如何继续用 AI，但不再完全依赖 AI

可以继续让 AI 协助，但把问题从“替我完成”逐渐改成下面的形式：

- “我认为这个函数的输入是这些、输出是这些，帮我检查理解有没有错。”
- “先不要改代码，让我猜错误位置，你再指出遗漏的证据。”
- “请给我一个最小失败样例，我自己写校验。”
- “我已经完成修改，请检查哪些边界还没有测试。”

每次让 AI 写了新代码后，自己补三句话：它新增什么行为；在哪个入口调用；失败会怎么处理。如果这三句话说不出来，先不要把这部分当作自己掌握的项目亮点。

代码量和术语数量不是学习成果。能解释一次设计取舍、独立定位一次错误、写出一项有意义的测试，才是你逐渐拥有这个项目的证据。
