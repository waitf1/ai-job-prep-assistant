# 第四阶段：Agent 工作流说明

## 目标

第四阶段将系统从“单次大 Prompt 输出整份分析”升级为“固定顺序、多步骤、可展示中间结果的 Agent 工作流”。

核心流程：

```text
输入岗位 JD 与个人资料
-> JD 解析
-> RAG 检索
-> 能力匹配
-> 简历建议
-> 面试题生成
-> 页面分步展示结果
```

本阶段的 Agent 不追求复杂自主决策，而是优先实现一个可控、可解释、适合演示的固定工作流。

## 为什么需要 Agent 工作流

第三阶段虽然已经具备 RAG 检索能力，但分析仍然是一次性输出，存在几个问题：

- 岗位要求提取、匹配分析、简历建议、面试题都混在一起，不利于用户理解；
- 页面只能看到最终结果，中间过程不透明；
- 后续如果要接入 Tool Calling，很难找到清晰的步骤边界；
- 单个 Prompt 负担过重，不利于后续单独优化某一个环节。

Agent 工作流的意义是把复杂任务拆成多个明确步骤，由代码固定编排顺序，大模型只负责各步骤的理解与生成。

## 当前实现

新增模块：

```text
app/services/
├── workflow_types.py        # 工作流结果对象
├── prompt_utils.py          # Prompt 读取与 JSON 解析
├── jd_analyzer.py           # JD 结构化解析
├── resume_advisor.py        # 简历建议生成
├── interview_preparer.py    # 面试题与补强建议生成
└── job_prep_workflow.py     # 固定顺序工作流编排
```

新增 Prompt：

```text
prompts/
├── jd_analysis_system.txt
├── jd_analysis_user.txt
├── match_analysis_system.txt
├── match_analysis_user.txt
├── resume_advice_system.txt
├── resume_advice_user.txt
├── interview_prep_system.txt
└── interview_prep_user.txt
```

### 工作流结果结构

当前已定义以下结果对象：

- `JDAnalysisResult`
- `MatchAnalysisResult`
- `ResumeAdviceResult`
- `InterviewPrepResult`
- `WorkflowRunResult`

这样每一步都有明确输入输出，不再依赖一个大字符串在多个模块之间传递。

### Step 1：JD 解析

系统先将岗位 JD 转为结构化结果，提取：

- 岗位职责；
- 必备技能；
- 加分项；
- AI 关键词；
- 面试关注点。

这些结果既用于页面展示，也用于后续 RAG 检索和匹配分析。

### Step 2：RAG 检索

如果当前是 RAG 模式，系统会基于 JD 解析结果生成检索查询，再从个人资料库中搜索最相关的片段。

页面会展示：

- 本次使用的检索查询；
- 命中的资料片段；
- 每个片段的来源和编号。

如果当前是普通分析模式，则不会执行资料库检索。

### Step 3：能力匹配

系统根据以下信息生成匹配分析：

- 简历正文或补充说明；
- 岗位 JD 原文；
- JD 结构化结果；
- RAG 检索片段。

输出包括：

- 当前匹配点；
- 当前缺口；
- 证据说明。

### Step 4：简历建议

系统将简历建议拆成两类：

- 当前可以直接修改的表达；
- 完成补充项目后可新增的表达。

这样更符合真实求职场景，也能减少“把未来计划写成已完成经历”的问题。

### Step 5：面试题生成

系统根据岗位要求、匹配分析和个人资料，生成：

- 针对性面试问题；
- 短期补强建议。

这一步让项目不只停留在“分析岗位匹配”，而是进一步进入“面试准备”。

## 页面变化

`app/main.py` 中的“开始分析”按钮现在触发的是固定顺序工作流，而不是单次分析函数。

分析完成后，页面会按步骤展示：

- Step 1：JD 解析；
- Step 2：RAG 检索；
- Step 3：能力匹配；
- Step 4：简历建议；
- Step 5：面试题生成。

这种设计有两个好处：

- 用户可以看到每一步到底做了什么；
- 后续可以更容易把每一步升级为 Tool Calling 或更复杂的 Agent 能力。

## 当前边界

当前版本的 Agent 工作流仍然是基础版，不处理：

- 自主决策是否跳过某一步；
- 多轮推理与循环调用；
- 模型自行选择工具；
- 多 Agent 协作；
- 多轮模拟面试对话。

也就是说，本阶段的 Agent 更接近“固定流程编排器”，而不是完全自主的智能体。

## 当前已知待优化项

以下问题不影响当前第四阶段核心验收，但建议后续统一优化：

- 目前各步骤依赖模型按 JSON 格式输出，后续可增强解析鲁棒性；
- 多步骤调用会增加整体耗时，后续可优化加载体验和错误提示；
- 还没有为工作流新增自动化测试，当前主要依赖手动验证、`compileall` 和 lint 检查。

## 验收标准

本阶段需要验证：

- 普通模式下能跑通 `JD 解析 -> 能力匹配 -> 简历建议 -> 面试题生成`；
- RAG 模式下能跑通 `JD 解析 -> RAG 检索 -> 能力匹配 -> 简历建议 -> 面试题生成`；
- 页面能分步展示每一步中间结果；
- 简历建议与面试题不再混在一个大段输出里；
- 某一步出错时，页面能给出明确异常提示。

## 面试表达

可以这样解释本阶段：

```text
我在项目中没有直接做一个完全自主的复杂 Agent，而是先实现了一个固定流程的 Agent 工作流。系统会先解析岗位 JD，再结合 RAG 检索到的个人资料片段，依次完成能力匹配、简历建议和面试题生成，并在页面中展示每一步中间结果。这样既能提高分析过程的可解释性，也为后续接入 Tool Calling 打下了清晰的步骤边界。
```

## 下一阶段方向

下一阶段可以做 Tool Calling，将当前固定流程里的关键步骤进一步封装成可调用工具。

推荐优先封装：

- `parse_document`
- `search_profile_knowledge_base`
- `analyze_job_description`
- `generate_resume_advice`
- `generate_interview_questions`

这样后续就可以从“固定流程 Agent”逐步升级到“可调用工具的 Agent 系统”。
