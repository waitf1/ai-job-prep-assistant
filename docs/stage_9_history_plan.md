# 第九阶段计划：结果保存与历史复盘

状态：本计划已于 2026-09-08 落地。实际交互、数据边界和验证见 `stage_9_history.md`；下文保留原实施计划供对照。

## 目标与交互

- 岗位分析成功后提供“保存本次分析”；面试结束后提供“保存本次复盘”。首次采用用户主动保存，避免每次练习自动落盘。
- 页面提供历史列表、类型/时间筛选和详情查看。重启后仍可读取已保存结果。
- 支持删除单条历史记录；删除分析时保留已保存面试，通过可空关联解耦。删除历史不得影响简历库和项目 Chroma 数据。
- 可从历史分析再次准备面试，复用已保存的分析结果；生成新问题前校验当前可用上下文，不重新执行岗位分析。

## 建议实现顺序

1. 新建 `app/storage/`，用标准库 sqlite3 在独立的 `data/history.sqlite3` 建库，加入 schema 版本及初始化事务。
2. 定义明确的数据快照结构和序列化函数，只保存白名单字段，不序列化整个 session_state 或 LLM 客户端。
3. 实现分析与面试的保存、列表、详情和删除；一次保存使用稳定记录 ID，重复点击更新同一条记录，避免重复历史。
4. 接入页面保存按钮与历史详情，复用阶段八的完整分析及轮次展示组件。
5. 增加从历史分析启动面试的入口和上下文校验，再完成重启恢复及删除隔离测试。

## 数据范围

- 分析记录：ID、创建/更新时间、schema 版本、岗位 JD、模式、分析结果、简历引用与内容指纹、采用的证据及必要来源信息。
- 面试记录：ID、可空的关联分析 ID、轮数、题源、每轮问题/原始回答/完整反馈、最终复盘及创建时间。
- 不保存 API Key、环境配置或上传原文件副本；题库原文继续仅限当前会话，已实际出题的问题可作为面试记录保存。
- 不额外复制完整简历。再次面试时检查简历库引用和指纹；简历已删除、发生变化或原分析使用临时简历时，提示重新提供/选择，再确认使用。禁止以历史占位说明充当项目经历。
- 理论题重新启动仍需 JD；题库模式重新启动仍需当前会话上传有效题库。

## 验收与测试

- 临时数据库验证建库幂等、序列化往返、中文及多行回答、重复保存不重复建记录。
- 模拟应用重启后读取完整分析与每轮反馈，无需再次调用模型。
- 删除分析不会删除已保存复盘；删除任意历史不会触及简历库、题库上传或 Chroma 集合。
- 缺失/变更简历与缺失题库时阻止项目/题库面试；只看历史不要求原始资料仍存在。
- 数据库锁定、损坏、写入失败时提示错误，当前页面结果仍可查看并再次保存。
- 新增 AppTest 覆盖保存、历史详情和再次面试，最后运行全部 unittest 回归。

本阶段不包含登录、多用户、云同步、自动投递、复杂统计看板或题库持久化。
