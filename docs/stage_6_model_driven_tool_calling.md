# 第六阶段：模型驱动 Tool Calling 说明

## 目标

本阶段在第五阶段“代码驱动 Tool Calling”的基础上，引入有限的模型决策能力。

系统仍由代码控制完整主流程：

```text
JD 解析 -> 能力匹配 -> 简历建议 -> 面试题生成
```

但在 RAG 模式下，是否检索个人资料库、使用什么检索 query，改由模型决定。

本阶段不实现完整的自主 Agent，不包含 ReAct 循环、多轮反思、多 Agent 协作或全工具自由编排。

## 工作流变化

```text
用户输入
-> JD 解析工具
-> 模型决策器 ToolPlanner
   -> 决定跳过检索 -> 能力匹配
   -> 决定调用检索工具 -> search_profile_knowledge_base -> 能力匹配
-> 简历建议工具
-> 面试题生成工具
-> 页面展示结果与调用过程
```

普通分析模式不读取资料库，也不会调用模型决策器；行为与之前保持一致。

## 核心实现

### 1. 工具 Schema

`BaseTool` 新增了工具 Schema 描述能力：

- 工具名称；
- 工具用途说明；
- 输入参数类型、描述和必填规则；
- OpenAI-compatible function tool 格式转换。

其中 `search_profile_knowledge_base` 明确声明了两个参数：

- `query`：根据岗位需求和个人经历构造的检索查询；
- `top_k`：最多返回的资料片段数量。

这使模型可以理解“有什么工具可以使用、工具能做什么、调用时应传入什么”。

### 2. 支持模型返回 Tool Call

`LLMClient` 新增 `chat_with_tools(...)`：

- 将工具 Schema 一并发送给 OpenAI-compatible 模型服务；
- 读取模型返回的 `tool_calls`；
- 保留普通文本内容，兼容模型选择“不调用工具”的情况。

模型服务需要支持 OpenAI-compatible 的 Function Calling / Tool Calling 格式；如果所选模型或网关不支持，模型可能只返回文本，此时系统会按约定读取 JSON 形式的“不检索”决策。

### 3. ToolPlanner 决策器

新增 `ToolPlanner` 服务，输入包括：

- 当前模式；
- 补充说明或简历正文；
- 岗位 JD；
- JD 结构化分析结果；
- 资料库可用状态；
- 可用的知识库检索工具。

它只负责一个小范围决策：

1. 当前分析是否需要额外检索个人资料库；
2. 若需要，构造检索 query 并请求调用 `search_profile_knowledge_base`。

它不负责生成最终的岗位匹配结论，也不负责控制后续步骤顺序。

### 4. 安全的工作流边界

即使模型输出了工具调用，代码仍会负责：

- 只允许使用已经注册的资料库检索工具；
- 只执行一次检索；
- 继续固定执行能力匹配、简历建议和面试题生成；
- 在检索工具失败时保留具体失败工具和错误信息。

因此，该版本是“模型参与局部决策”，不是将整个系统控制权交给模型。

## 页面展示

RAG 模式的 `Step 2：RAG 检索` 会展示：

- 模型是否决定检索；
- 决策说明；
- 决策方式：模型发起工具调用，或模型直接决定跳过；
- 如果实际检索，展示模型生成的 query；
- 最终检索到的资料片段。

“工具调用过程”区域继续展示实际执行的工具及其输入、输出摘要。只有模型决定检索时，才会出现 `search_profile_knowledge_base` 的执行记录。

## 验收情况

已通过以下基础验证：

- Python 编译检查：`python -m compileall app`；
- 普通模式：跳过检索，后续固定工作流正常执行；
- RAG 模式：模型返回工具调用时，工作流会执行资料库检索；
- RAG 模式：模型决定跳过时，工作流不会执行检索，后续步骤仍正常执行；
- 静态检查未发现新增 lint 错误。

对应自动化测试位于 `tests/test_model_driven_tool_calling.py`。

## 已知边界与后续优化

当前阶段仍有以下边界：

- 只允许模型决定一个工具：资料库检索；
- `top_k` 仍由用户在页面设置，模型生成的 `top_k` 不会覆盖页面配置；
- 模型未调用工具时，只支持约定 JSON 的“跳过检索”返回；
- 还没有检索质量评估、失败重试或结果阈值过滤；
- 尚未支持模型根据首次检索结果发起第二次检索。

后续建议优先按以下顺序优化：

1. 为工具调用、planner 决策和检索失败场景补充更多回归测试；
2. 完善检索质量控制：相似度阈值、重排序、动态 `top_k`；
3. 将能力匹配也封装为工具，统一工具边界；
4. 支持有限的“检索结果不足时二次查询”；
5. 最后再探索多工具自主选择与受限 ReAct 循环。

## 面试表达

```text
我先把岗位分析拆为固定、可控的 Agent 工作流，并将 JD 解析、知识库检索、简历建议和面试题生成封装为标准化工具。在此基础上，我没有直接放开全流程自治，而是先让模型在 RAG 模式下决定是否调用知识库检索工具，并生成检索 query；主流程顺序、工具白名单和错误处理仍由代码控制。这样既实践了模型驱动 Tool Calling，也避免了自主 Agent 带来的不可控性。
```
