# 第五阶段：Tool Calling 说明

## 目标

第五阶段将系统从“固定流程直接调用服务”升级为“通过标准化工具执行关键步骤，并记录工具调用过程”。

核心流程：

```text
用户输入
-> 固定流程工作流
-> 调用标准化工具
-> 返回工具结果
-> 记录工具调用日志
-> 页面展示分析结果与工具调用过程
```

本阶段仍然不追求让模型自主选择工具，而是优先把工具边界、输入输出和日志结构打牢。

## 为什么需要 Tool Calling

虽然第四阶段已经实现了固定流程 Agent 工作流，但如果所有能力都只是服务层内部互相调用，仍然存在几个问题：

- 各步骤的能力边界不够明确，不利于后续扩展；
- 页面只能展示工作流步骤，不容易展示“调用了哪些能力”；
- 如果以后要让模型自主选择工具，就缺少标准化工具接口；
- 某一步失败时，定位问题的粒度还不够清晰。

Tool Calling 的作用，是把系统已有能力包装成独立工具，让工作流调用的是“工具接口”，而不是直接依赖底层服务实现。

## 当前实现

新增模块：

```text
app/tools/
├── __init__.py              # 工具层导出与懒加载
├── tool_types.py            # 工具结果与调用记录
├── base.py                  # 工具基类
├── document_tools.py        # 文档解析工具
├── knowledge_base_tools.py  # 资料库检索工具
└── analysis_tools.py        # JD 解析 / 简历建议 / 面试题工具
```

### 工具协议

当前定义了统一的工具结果结构：

- `ToolCallRecord`
- `ToolResult`
- `ToolExecutionContext`

每个工具都会记录：

- 工具名；
- 输入摘要；
- 输出摘要；
- 是否成功；
- 错误信息。

### 第一批工具

当前已封装的第一批工具包括：

- `parse_document`
- `search_profile_knowledge_base`
- `analyze_job_description`
- `generate_resume_advice`
- `generate_interview_questions`

这说明项目已经具备了基础 Tool Calling 结构，而不仅仅是普通的服务层调用。

### 工作流接入方式

当前固定流程工作流会通过工具层执行部分关键步骤，例如：

- 用 `analyze_job_description` 工具做 JD 解析；
- 在 RAG 模式下用 `search_profile_knowledge_base` 工具检索资料库；
- 用 `generate_resume_advice` 工具生成简历建议；
- 用 `generate_interview_questions` 工具生成面试题。

能力匹配步骤目前仍保留在工作流内部，没有强制工具化。这是刻意保留的简化设计，用来控制本阶段复杂度。

## 页面变化

`app/main.py` 在原有 Agent 工作流结果基础上，新增了“工具调用过程”展示区域。

当前页面可以看到：

- 本次共调用了几个工具；
- 每个工具的名称；
- 每个工具的输入摘要；
- 每个工具的输出摘要；
- 工具是否执行成功；
- 如果失败，会显示对应错误信息。

这部分内容的主要价值，不是改变最终分析文本，而是让用户和开发者都能更清楚地看到系统的执行过程。

## 当前边界

当前版本的 Tool Calling 仍然是基础版，不处理：

- 模型自主决定调哪个工具；
- 多轮 ReAct 或循环调用；
- 多 Agent 协作；
- 远程工具注册或 MCP 接入；
- 基于工具调用结果进行二次决策。

也就是说，本阶段实现的是“代码驱动的工具调用”，还不是“模型驱动的工具调用”。

## 当前已知待优化项

以下问题不影响当前第五阶段核心验收，但建议后续统一优化：

- 当前工具调用日志以摘要为主，后续可增加更丰富的调试信息；
- 工具失败时虽然可以看到失败工具名，但还可以进一步优化失败后的恢复策略；
- 目前 `能力匹配` 还没有工具化，后续可以继续统一工具边界；
- 还没有为工具层和工具日志补充自动化测试；
- 页面中的工具调用过程更偏调试展示，后续可以优化为更适合演示或更适合开发的两套视图。

## 日后优化路线

建议后续按以下顺序继续演进：

### 1. 补齐工具层覆盖范围

优先把当前仍在工作流内部的能力也工具化，例如：

- `generate_match_analysis`
- `build_profile_knowledge_base`
- `reset_profile_knowledge_base`

这样可以让项目的能力边界更统一。

### 2. 提升工具调用日志可读性

可继续增强：

- 展示更清晰的输入参数结构；
- 区分“用户可读日志”和“开发调试日志”；
- 对失败工具提供更明确的排查提示。

### 3. 引入模型驱动的工具选择

等当前工具层稳定后，再升级到真正更像 Tool Calling 的形式：

- 让模型判断是否需要调用资料库检索；
- 让模型决定调用哪个工具；
- 让模型根据工具结果继续下一步决策。

这一阶段才会更接近“模型自主调用工具”的完整形态。

### 4. 接入更复杂的 Agent 能力

在模型驱动工具调用稳定后，再考虑：

- 多轮工具调用；
- 自主计划与反思；
- 多 Agent 协作；
- 更复杂的面试对话系统。

### 5. 补齐工程质量

最后再统一做工程完善工作：

- 为工具层补自动化测试；
- 为工作流补回归测试；
- 优化异常处理与重试策略；
- 梳理文档与阶段状态同步。

## 验收标准

本阶段需要验证：

- 至少 3-5 个核心工具可以独立调用；
- 普通模式和 RAG 模式都能通过工具层跑通完整流程；
- 页面能展示工具调用过程；
- 工具失败时能明确定位到是哪一个工具；
- 项目整体功能与上一阶段保持兼容。

## 面试表达

可以这样解释本阶段：

```text
我在项目中将 JD 解析、知识库检索、简历建议生成、面试题生成等能力封装成了标准化工具，并让固定流程工作流通过工具层执行关键步骤。同时我为工具调用增加了统一的输入输出摘要和调用日志展示。这样系统虽然还不是完全自主的 Agent，但已经具备了 Tool Calling 的基础工程结构，后续可以自然升级到模型自主调用工具的形式。
```

## 下一阶段方向

下一阶段可以优先在以下两个方向中二选一：

- 继续做“模型驱动的 Tool Calling”，让模型决定调用哪些工具；
- 先做工程优化，补齐工具层测试、日志、异常恢复与文档同步。

如果目标偏演示和面试表现，建议优先做“模型驱动的 Tool Calling”；如果目标偏稳定性和长期维护，建议优先做工程优化。
